# ADR 0005: Write the missing documentation generator

**Status:** Accepted
**Date:** 4 November 2026

## Context

`frontend/src/data/docs/wikiPages.js` begins with:

> Auto-generated by the documentation build script. Do not edit by hand;
> regenerate from docs/wiki/Home.md and TECH_STACK.md.

No such script exists. `scripts/` holds only the clinical-fixture generator. No
`package.json` script and no CI step references `wikiPages` or the wiki. Git
history shows no deleted generator either — the file was committed alongside
its supposed sources.

The consequence is a trap. The documentation module carries a generated-file
banner, but nothing can regenerate it. A developer adding a wiki part either
hand-edits a file that says not to be hand-edited, or leaves the documentation
out of step with the wiki. The next agent has no way to tell which of the two
files is authoritative.

The Program Management module needs a new wiki part, so this gap is hit
immediately rather than eventually.

## Decision

**Write the generator, and check its output in CI.**

A small Node script parses the platform wiki and the tech-stack document and
emits the documentation module: the section list, the page list, the page
content map, and the heading-owner map used for the in-page table of contents.
It is wired as a documentation build script, and CI verifies that the committed
module matches what the script produces.

The wiki remains the source of truth. The generated module remains generated.
The difference is that now it genuinely is.

## Consequences

- A documentation change becomes two steps — edit the wiki, run the build — and
  the CI check makes a forgotten second step a failure rather than a silent
  drift.
- The generator has to handle the wiki's structure: the front matter before the
  first part becomes the start-here page, each `# Part N` becomes one page, and
  the headings within each page become the table-of-contents entries.
- The script replaces a build step that evidently existed outside this
  repository. Anything that tool did that the new script does not will show up
  as a diff on the first run, and that diff must be reviewed rather than
  accepted blindly.
- The wiki's own table of contents and the generated page list must agree. The
  generator is the thing that checks it.

## Alternatives considered

**Hand-patch the generated module for this change and note the gap.** Rejected:
it entrenches the trap. The next documentation change repeats the same
violation of the file's own instruction, and no agent can discover the
convention because the thing that would teach it is missing.

**Drop the generated module and read the wiki at runtime.** Rejected: the wiki
is bundled at build time by design, so this is a build-architecture change, and
it does not belong in a feature branch.

**Regenerate by hand once and leave it.** Rejected: this is the same as
hand-patching, with extra steps.
