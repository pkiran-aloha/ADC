# Welina UX audit and remediation

Audited October 14, 2026 against the supplied `redesign-existing-projects` skill. Scope: the React analytics demo, recording/annotation flows, exports, responsive navigation, and the static GitHub Pages experience. The existing React 19, Vite 8, Tailwind CSS **v4**, shared clinical fixture, and .NET API remain in place.

## Baseline

A Chromium review at 1440 × 1040 and 390 × 844 found a **589px document on a 390px viewport** (199px overflow). An axe WCAG A/AA scan of the default desktop view reported four unnamed selectors and three text-contrast failures. Automated checks do not replace a manual accessibility audit.

## Implementation priorities

1. **Access and correctness:** eliminate horizontal page overflow, unnamed selectors and contrast failures; repair dialog/keyboard behavior, validation, annotation context, missing-versus-zero handling and export failure feedback.
2. **Visual system:** change fonts, reduce the palette, strengthen hierarchy, consolidate summaries and make the mastery view compact; retain a generous, readable target-analysis canvas.
3. **Polish and resilience:** consistent hover/pressed/focus states, real loading/empty/error paths, accessible chart equivalents, honest demo information, branding/static pages and regression coverage.

## Deliberate omissions

- No stock team photos, marketing card grids, carousels, pricing tables, testimonial walls, decorative animation, or parallax: this is a clinical data workspace, not a marketing site. Texture and restrained spacing provide depth without obscuring data.
- No theme switch: the interface intentionally uses one coherent light theme.
- No cookie-consent banner: the app sets no tracking cookies and includes no analytics/advertising SDK. Demo localStorage is functional storage; the privacy page explains it. Reassess consent if tracking is introduced.
- No clinical/compliance claims. GitHub Pages still hosts the static demo, not the .NET API or a production patient-record system.

## Analytical charting (October 2026)

Behavior analysts live in their graphs: they inspect level, trend, variability, immediacy and overlap; drill from a weekly summary to the trials behind it; check whether measurement was reliable and treatment was delivered as written; and look for the antecedents, consequences and conditions that predict problem behavior. This update turns the charts into that workflow without adding chart dependencies (all visuals are hand-written, labeled SVG or HTML tables).

| Need | Before | Now |
|---|---|---|
| Data depth | 3 clients, ~2 months, 297 rows of aggregate values; ABC records hand-written. | Simulated 26-week fixture for 5 clients: 589 appointments, 3,676 rows with per-trial prompt codes, interval scores, episodes, fluency errors and IOA; 826 ABC records sampled from function-specific behavior models; phase histories consistent with structured mastery rules; supervision, fidelity and setting events. |
| Reading a point | Native `<title>` tooltips only. | Accessible tooltip, keyboard crosshair (arrows/Home/End with a polite live announcement), and select-to-drill inspector (month → week → day → session → trial chips, interval grid, episodes, IOA, fidelity, supervision, setting events, ABC context). |
| Chart functions | Average and two trend options. | Median, moving average, stability envelope, condition means, mastery criterion, projection band, IOA markers, ratio scale, split-middle trend, CDC criterion lines; prompt-level and celeration views; timeline zoom with two labeled range inputs. |
| Interpretation | None beyond the regression equation. | WWC six-feature table, PND/PEM/NAP/Tau/Tau-U with literature bands, conservative dual-criterion, mastery efficiency (sessions/trials/days to criterion), decision prompts keyed to BACB TCO tasks, data-quality and context breakdowns. Copy states these support—not replace—visual inspection. |
| ABC analysis | Stacked daily counts and a paged log. | Clickable bars and filter chips; antecedent/consequence heat maps (counts, conditional %, lift) that open matching records; descriptive function profiles from pre-intervention records compared with the FBA hypothesis (with an explicit “descriptive ≠ functional analysis” caveat); scatterplot that distinguishes unobserved time; flow diagram; setting-event rate ratios; escalation chains; intensity trend. |
| Prediction | None. | Poisson next-session forecast (exposure offset, trend, setting events) with scenario controls and 80% ranges, two-week trend outlook, naive-Bayes situation explorer. Every model reports rolling-origin performance on later sessions against a naive baseline and labels itself when it is not better. |
| Overview | Cumulative mastery only. | Weekly progress map (targets × 12 weeks, goal- or baseline-relative color with text values) whose cells open the target analysis at that week; Service & data quality section (hours vs authorization, attendance, IOA coverage, fidelity, cancellations, RBT supervision vs the BACB 5% minimum). |

Accessibility and performance decisions:

- Heat maps are real tables with captions and 44px button cells whose labels carry the value, sessions and context; color is never the only encoding (values are printed) and cell ink is pure black or white chosen by luminance so every cell clears 4.5:1.
- Only one `svg.chart-svg` renders per section at a time; auxiliary charts use separate classes and named, focusable scroll regions. Interactive SVG marks are pointer conveniences—keyboard users have the crosshair, inspector navigation buttons, tables and filters.
- New panels avoid `role="alert"` and duplicate control names so screen-reader and test landmarks stay unambiguous.
- The fixture is a separate cacheable chunk (~129 kB gzipped); Patterns, Forecast, the progress map and the service section are lazy chunks; localStorage writes only the keys that change.

## Graphing and recording speed (October 2026)

Feedback from a demo of the analytics module: phase lines covered data points, phase titles were truncated, the vertical axis could not be set, there were not enough graph types for the different measurement tools, and recording a session one target at a time was slow. All visuals stay hand-written labeled SVG/HTML — no chart dependency is added.

| Need | Before | Now |
|---|---|---|
| Phase changes | A 2.5px solid line drawn through the data with a 150px label chip truncated at 22 characters, staggered into at most two rows. | A **condition strip** above the plot: the target's phase history and manual phase lines become labelled spans whose titles are fully readable (truncated only when a span is too narrow, with the full label on hover). The change itself is a thin, semi-transparent divider drawn **behind** the series with a white casing — it never covers a data point. *Phase labels* toggles the strip; *Values* prints each plotted measurement. |
| Vertical axis | Always auto-scaled: 0–100 for percentages, 15% headroom otherwise, with fixed 0/25/50/75/100 gridlines. | The clinician fixes the minimum, the maximum, or both from a **Y axis** control; blank scales that end to the data. Gridlines use readable 1/2/2.5/5 steps, out-of-range points are clipped (never dropped) and the chart states how many fall outside — they stay in the data table, CSV and SVG/PNG exports. Reversed or negative ranges are reported inline instead of silently rescaling. |
| Graph types | One line chart, plus prompt-level and celeration views for two measurement types. | **Plot types for every quantitative tool** — line, grouped bars, points (variability) and a cumulative record — plus specialist views per tool: prompt levels and a **trial-by-trial strip** (one cell per trial, coloured by the prompt recorded, with the independent share) for trial-by-trial; an **episode** view (each session's total split into recorded episodes) for duration; **celeration** for fluency and for rate-measured frequency. |
| Recording speed | One target per dialog: choose a target, fill its measurement, save, reopen for the next target. | **Session recording.** The recorder opens on *Whole program*: one shared date, clinician and optional session length, then one compact row per target. Tick what was worked on, save once, and *Save & next session* keeps the sheet open, cleared, and moved to the client's next appointment. *Copy last session* refills every row from its previous observation, *Apply minutes to all rows* shares one observation length, each row can record a phase change, and the clinician/program/target set is remembered per client. *Single target* keeps the old one-target flow. |
| Recording correctness | Unchanged semantics. | Unchanged: a blank field never becomes zero, and *Observed* (measured zero) stays distinct from *Not tracked*, which is kept missing in raw CSV/ZIP exports. Validation is per row, focuses the first invalid input, and writes the whole session with one save. |

## Feature-request round two (October 2026)

The demo was reviewed by users of a competing analytics product. Their 31 requests (multi-graph reporting, manual and bulk data entry, annotation reuse, graph cleanliness controls, access levels, live session visibility) were implemented against the same fixture, with no new runtime dependencies and the same hand-written SVG approach.

| Request group | Before | Now |
|---|---|---|
| Multi-target / multi-graph analysis | Each graph plotted one target; a behaviour comparison plotted several unitary targets but no combined line. | *Summary* adds a combined or averaged series across the visible targets (totals are refused for percentage measures and the reason is stated), the behaviour-reduction flow selects several targets with presets, and *Chart orientation → Dates on the left* flips time onto the vertical axis with annotations, milestones and notes moved to the alternate axis. |
| Reporting and exports | One family per export: chart images, a raw CSV, a ZIP of every target. No printable document. | A **Reports** section builds a print-ready HTML document from four templates (clinical review, authorization request, reassessment, treatment-plan progress) with every selected graph, mastery criteria, phase changes, notes, learner/service summary, goal list, acquisition-rate table and signature blocks — downloaded or opened in a print view for a PDF. A **target roster** lists current, maintenance or mastered targets with an introduction/mastery date filter and CSV export. The raw CSV gained session date, session context, service code, setting, session therapist, session status and data source columns. |
| Annotations | One target per note, line or range; note text only in the tooltip. | Phase lines, ranges and notes carry an *Apply to* list (current target, other targets in the program, or all), which writes one copy per target and reports duplicates that were skipped. Graph notes are drawn on the chart as staggered labelled rows with leader lines so the full text is readable without hovering, and they travel into reports and exported SVG. |
| Data entry and import | Sessions only, one target at a time (whole-session recorder for one program). | **Add or import data** records probe, school, paper, assessment, historical or session data with its collection source, date, time, clinician, measurement fields and an optional note that explains an unusual value — without a lesson note. **Import spreadsheet** accepts pasted rows or a CSV/TSV file, matches columns by name, previews every row with its status, converts ten-trial percentages, explains each assumption as a row note, and offers a template plus a *rows to fix* download. |
| Graph cleanliness | Missing dates could be shown or hidden, but every session was plotted. | *Graph view* controls: dates with no data are hidden by default, sessions below the organization's minimum trial count can be suppressed (floor shown, override box, counts of what was hidden stated above the plot), the data-point marker is customizable (solid circles by default for one target, a distinct sequence for several), and the chart states when values are outside a fixed axis. |
| Mastery and status | Mastery used per-target consecutive-session rules; program status lived in Program setup; phase history held the dates but the chart did not show them. | Behaviour-reduction mastery now follows a baseline-plus-percentage-reduction rule from `clinicalStandards.behaviorReduction` (80% below baseline sustained 14 days by default) and reports met/days-to-go in the progress tab. Introduction, mastery and maintenance dates appear as labelled milestones on the chart and in the target timeline with days-to-mastery and acquisition rate. **Program status can be changed from the analytics workflow** with a reason, written to the program's status history. |
| Data integrity and access | Anyone could edit any point; no role model; supervision/IOA context lived only on the appointment. | A **correct/delete** flow in the observer inspector validates the new values, requires a reason and keeps a change-history entry; corrections to a billed appointment are flagged *Post-billing change* instead of being blocked or quietly rebilled. Supervision and IOA observations are listed with the session and excluded from every learner total. An **Access** switch demonstrates full versus view-only analytics: view-only keeps reading, analysis and exports and disables entry, annotations, axis/graph configuration, program status and the demo reset, with a persistent banner and one-click switch back. |
| Live operations | Service quality was retrospective. | **Session activity** shows the fictional current day: scheduled, in-progress and finished appointments, observations and minutes recorded per appointment and target, the last recorded time, which appointments still need documentation, and a seven-day observation strip — no session note required. |
| Time of day | ABC patterns aggregated into blocks and weekdays only. | A **time-of-day scatterplot** plots every recorded event by its timestamp on a 24-hour axis with intensity-sized, intensity-coloured dots, plus the share of events by part of day, peak hour, and earliest/latest event. |
| Performance | Charts recomputed synchronously and could feel unresponsive while filters changed. | Session-derived work uses deferred values with an *Updating chart* status, the summary/statistics pipeline is memoized, and the new sections (Reports, data entry) load as their own chunks. |
| ABC conditional probability | Already shipped (counts, conditional probability and lift matrices). | Unchanged; the request is satisfied by the existing heat maps and their *open matching records* drill-down. |

Accessibility and implementation decisions:

- New controls reuse the existing label/toggle/popover patterns; every new table is a real `<table>` with a caption or accessible name, every new region is focusable with a label, and the marker shapes are chosen to stay distinguishable without colour.
- Import and manual entry are keyboard-complete: the tab control is a segmented button group, errors are announced `role="alert"` per field, and the preview table is a named scroll region.
- `npm run smoke` renders every analytics section with `react-dom/server` on the real fixture. It was added after it caught two runtime faults that the bundle could not: a `useMemo` reading a target before its declaration, and missing marker/label imports in `TargetChart` (both would have thrown on first paint).

## Feedback round three — workflow presentation and layout polish (October 2026)

Two reviews of the finished demo: (1) the page “just dumps everything at once as one continuous whole,” which is overwhelming when giving feedback, and (2) many components do not align and text overflows. The interface now opens on one workflow at a time and the remaining layout faults are corrected.

| Need | Before | Now |
|---|---|---|
| Presentation | Twenty sections stacked into a ~10,400px scroll; finding anything meant scrolling past unrelated graphs. | **Five workflow tabs** group the screens around naturally occurring jobs: *Progress overview* (client summary, mastery, weekly progress map), *Target analysis* (the deep-dive graph, conditions and mastery annotations), *ABC observations* (patterns, scatterplot, forecast, event log), *Service & data quality* (dosage, IOA, fidelity, supervision, cancellations), *Reports* (builder and target roster). Each tab is its own screen (~2,100px at desktop); a 1440px view covers most of a workflow without scrolling. |
| Workflow navigation | Sidebar anchors on a long page; hash scrolling. | An ARIA tab strip (roving tabindex, Home/End/arrow keys) with a session snapshot chip (clients · observations · targets · week · data sources) that reuses the existing snapshots; the sidebar and URL hash stay in sync with the active workflow; `#<workflow>` links and the weekly-map drill-down open the right tab. Screens mount on first visit so chart state, filters and lazily-loaded analyses survive switching back and forth. Below 900px the snapshot moves inline under the page heading and the tab strip becomes a horizontal scroller. |
| Tablet header | Between 1,024 and 1,279px the sticky header clipped the client picker and Record CTA. | The tablet header row is a flex wrap; below 1,024px the record/import actions live in the drawer (already tested), and every control stays inside the viewport at 320–1,440px. |
| Alignment | Legend group buttons left-align to the label instead of the group row; status filter squeezed into a narrow column; roster date filters stacked into a tall column. | Legend groups wrap their buttons in a full-width flex row under each label; the status filter and roster actions become wide segmented rows; the three roster date filters share one grid row. |
| Text overflow | Chart note labels truncate, wrap awkwardly or collide with date labels; roster target names wrap in a squeezed table; long week labels clip the week-strip bars; ABC log overflows the content width at desktop. | Note labels wrap to at most two lines inside a bordered box below the condition strip with a leader line to their point; the reports layout stacks a compact builder over a full-width roster so all six columns fit with single-line names; week labels use a fixed short format with the full date in title/tooltip while bars keep a minimum height; the ABC table has real minimum widths inside its named scroll region. |
| Content | “1 targets” copy; duplicate long labels. | Pluralisation fixed (“1 target”), a handful of date/unit labels tightened (e.g. “Avg 23 d to mastery”). |

Verification additions: the axe layout-widths scenario now exercises **every** workflow tab at 320/390/768/1024/1440/1920px (60 scans), new tab-semantics and workflow-state-persistence scenarios, and a DOM-level polish check (roster fit, note-label containment, legend alignment, header bounds, one-panel-per-tab).

### Scope and limitations

- The original UX pass left the fixture and backend unchanged; the analytical-charting update replaced the fixture with a simulated one (same schema plus optional fields) and added typed .NET models, phase-history mastery and a service-sessions endpoint. Measured values, raw records, six recording tools, annotation CRUD, setup/material inspection and exports are retained. Predictive models are transparent demonstrations on fictional data, evaluated on later sessions; they are not validated clinical tools, and descriptive ABC patterns are not a functional analysis.
- Automated axe checks and Chromium mobile emulation are not a WCAG certification or physical-device/screen-reader audit. Safari/Firefox, VoiceOver/TalkBack/NVDA and production-scale patient workflows need separate validation before any real clinical use.
- The .NET SDK is unavailable in this workspace, so no new local .NET build is claimed. The session-recording batch (`recordTrials` / `updateTargetPhases`) currently lives in the browser-local demo service; the API would need the equivalent bulk endpoints before it could back this flow.
- Chromium still cannot be installed with `npx playwright install chromium` in this workspace (the browser CDN is unreachable), so the suite was launched with a locally available headless Chromium through `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` in the page-estate validation round (see the note at the end of this section); the 61 scenarios (five new) were written against the production build and pass lint, and every section they touch renders under `npm run smoke`. The earlier note stands: the new scenarios were written against the production build and reviewed, while the chart itself was verified by server-rendering `TargetChart` (condition strip geometry, divider layering, bar/point/cumulative output, axis ticks under fixed bounds) and the section by server-rendering `ClientSpecificSection`. Run `npm run test:ux` where Playwright Chromium is available before merging. The existing CI API build remains configured. This static demo still does not host the API or authenticate/store production patient records.
- Implementation and local verification were performed on the working branch without a production deployment. Merging to `main` triggers GitHub Pages publication only after the workflow succeeds.
